# Wire Rust into Neovim's C core

nvim-oxi lets you write a Neovim plugin as a Rust `cdylib`. LuaJIT loads it with `require("name")` like any native Lua module, and from then on your code calls Neovim's exported `nvim_*` C functions directly. There is no msgpack-RPC process, so keymap callbacks, autocmds and `vim.schedule` work in-process, and nearly every function and option struct has a compile-time type. The cost comes from that same design. Each typed option struct mirrors one of Neovim's internal `#[repr(C)]` keyset layouts, so a binary is tied to one Neovim minor version. A layout change, even in a patch release, can abort the editor. **As of October 2026 the only crates.io release is still 0.6.0 (May 2025)**, which supports Neovim 0.10 and 0.11 only. Support for Neovim 0.12 exists only on git `main`, which has had no commits since 2026-05-17, and open issues show 0.12.x crashes in `set_hl` and `create_autocmd`. Adoption is narrow: about 1.1k stars and 58k downloads, with nomad (by nvim-oxi's own author) as the only major user. The large Rust-backed plugins, including blink.cmp, avante.nvim and fff.nvim, use plain **mlua in module mode** instead. Choose nvim-oxi when most of a plugin's logic must drive the Neovim API from Rust and you can pin a git revision. For a Rust compute kernel behind a Lua frontend, choose mlua.

## One cdylib, no RPC: how nvim-oxi plugs into Neovim

Most non-Lua plugins have traditionally talked to Neovim over RPC. The nvim-oxi README argues this forces everything through MessagePack serialization, "prohibiting things like attaching callbacks to keymaps or scheduling functions". nvim-oxi instead "leverages Rust's foreign function interface (FFI) support to hook straight into the Neovim C code, allowing feature parity with 'in process' plugins" ([README](https://github.com/noib3/nvim-oxi)). The mechanism is simple. The `#[nvim_oxi::plugin]` attribute emits a `#[unsafe(no_mangle)] extern "C" fn luaopen_<fn_name>`, which is the symbol LuaJIT's `require` looks for in a C module ([plugin.rs](https://github.com/noib3/nvim-oxi/blob/main/crates/macros/src/plugin.rs)). When Neovim loads the library, that entrypoint stores the `lua_State*` in a thread-local, initializes an arena and optionally libuv, calls your function, and pushes its return value onto the Lua stack ([entrypoint.rs](https://github.com/noib3/nvim-oxi/blob/main/src/entrypoint.rs)). The `nvim_*` functions are declared in `extern "C"` blocks with no link library on Unix, so they resolve against the running `nvim` binary at load time. On Windows they link as `raw-dylib` against `nvim.exe` ([options.rs](https://github.com/noib3/nvim-oxi/blob/main/crates/api/src/ffi/options.rs)). API calls pass Neovim's `LUA_INTERNAL_CALL` pseudo-channel, so Neovim treats them exactly like calls from Lua ([api/lib.rs](https://github.com/noib3/nvim-oxi/blob/main/crates/api/src/lib.rs)).

This design has three consequences. First, **your code runs on Neovim's main thread in Neovim's address space**, so long-running Rust code blocks the editor and a crash takes the editor down with it. Second, the module name, the library file stem and the `#[plugin]` function name must all match, or LuaJIT cannot find `luaopen_<name>`. On Windows a mismatch surfaces as `E5108: The specified procedure could not be found` ([issue #185](https://github.com/noib3/nvim-oxi/issues/185)). Third, some Neovim internals are not exported, so nvim-oxi works around them. For example, `schedule()` calls the Lua `vim.schedule` function because "the `nlua_schedule` C function is not exported" ([toplevel.rs](https://github.com/noib3/nvim-oxi/blob/main/src/toplevel.rs)).

### The API is the C API with `nvim_` dropped and builders added

The `nvim-oxi` crate is a facade over five workspace crates (`-api`, `-types`, `-luajit`, `-libuv` and `-macros`). Its public surface is `nvim_oxi::{api, api::opts, api::types, lua, libuv, mlua, conversion, serde}`, the value types `Object`, `Array`, `Dictionary`, `String` and `Function`, and the `print!`/`dbg!` macros, `schedule`, and `Result`/`Error` ([src/lib.rs](https://github.com/noib3/nvim-oxi/blob/main/src/lib.rs)). The naming rule is mechanical. `nvim_get_current_buf` becomes `api::get_current_buf`, and the `nvim_buf_*`, `nvim_win_*` and `nvim_tabpage_*` functions become methods on `Buffer`, `Window` and `TabPage` ([api/lib.rs](https://github.com/noib3/nvim-oxi/blob/main/crates/api/src/lib.rs)). Each function that takes an options dictionary instead takes a typed struct built with `XxxOpts::builder()...build()`. There are about thirty of them, covering autocmds, commands, extmarks, highlights, keymaps, `echo`, `exec` and more ([opts/](https://github.com/noib3/nvim-oxi/tree/main/crates/api/src/opts)). Callback arguments are typed too. A user-command closure receives `CommandArgs` with `args`, `bang`, `fargs`, `line1`/`line2` and so on ([command_args.rs](https://github.com/noib3/nvim-oxi/blob/main/crates/api/src/types/command_args.rs)). An autocmd callback receives `AutocmdCallbackArgs` and returns `bool`, where `true` deletes the autocmd ([create_autocmd.rs](https://github.com/noib3/nvim-oxi/blob/main/crates/api/src/opts/create_autocmd.rs)).

Values cross the boundary through two trait layers. `FromObject`/`ToObject` convert between Rust values and Neovim `Object`s for API calls. `lua::Pushable`/`lua::Poppable` move values on and off the Lua stack for function arguments, return values and the entrypoint's result ([conversion.rs](https://github.com/noib3/nvim-oxi/blob/main/crates/types/src/conversion.rs), [pushable.rs](https://github.com/noib3/nvim-oxi/blob/main/crates/luajit/src/pushable.rs)). `Function<A, R>` is a typed handle to a function stored in the Lua registry. `Function::from_fn` wraps a Rust closure, and `.call(args)` invokes a Lua function passed in from outside ([function.rs](https://github.com/noib3/nvim-oxi/blob/main/crates/types/src/function.rs)). To expose functions to Lua, you return a `Dictionary` of them from the entrypoint. The official `calc` example shows the full round trip, including a Lua callback invoked from Rust ([examples/calc.rs](https://github.com/noib3/nvim-oxi/blob/main/examples/calc.rs)):

```rust
use nvim_oxi::{Dictionary, Function, Object};

#[nvim_oxi::plugin]
fn calc() -> Dictionary {
    let add = Function::from_fn(|(a, b): (i32, i32)| a + b);
    let compute = Function::from_fn(
        |(fun, a, b): (Function<(i32, i32), i32>, i32, i32)| fun.call((a, b)).unwrap(),
    );
    Dictionary::from_iter([("add", Object::from(add)), ("compute", Object::from(compute))])
}
// Lua: require("calc").compute(function(a, b) return a + b end, 1, 41)
```

The `api` example registers a `:Greetings` command with `create_user_command`, sets an insert-mode keymap with `api::set_keymap(Mode::Insert, "hi", "hello", &Default::default())`, and toggles a floating window via `api::open_win(&buf, false, &WindowConfig::builder().relative(WindowRelativeTo::Cursor)...build())`. Shared state in that example lives in `Rc<RefCell<..>>`, because everything runs on one thread ([examples/api.rs](https://github.com/noib3/nvim-oxi/blob/main/examples/api.rs)). Custom structs are handled by the `mechanic` example. It implements `FromObject`/`ToObject` through `nvim_oxi::serde::{Deserializer, Serializer}` and then `Poppable`/`Pushable` on top, so a Lua table deserializes straight into a Rust struct ([examples/mechanic.rs](https://github.com/noib3/nvim-oxi/blob/main/examples/mechanic.rs)). When the typed API runs out, there are four escape hatches: `api::call_function`, `api::command`, `api::eval` and `api::exec2` ([vimscript.rs](https://github.com/noib3/nvim-oxi/blob/main/crates/api/src/vimscript.rs)). The optional `mlua` feature adds a fifth, `nvim_oxi::mlua::lua()`, which wraps Neovim's own `lua_State` as an `mlua::Lua` and gives dynamic access to `vim.*` ([src/lib.rs](https://github.com/noib3/nvim-oxi/blob/main/src/lib.rs)).

Coverage has real gaps. Feature requests for `vim.ui`, `vim.lsp` and `vim.diagnostic` have been open since July 2022, and treesitter support since 2024 ([issues](https://github.com/noib3/nvim-oxi/issues)). `vim.fn` bindings were still an open PR (#314) in June 2026 ([PRs](https://github.com/noib3/nvim-oxi/pulls?q=is%3Apr)). `api::call_function` arguments are not checked at compile time. One reported "panic" in `Window::call` turned out to be `((),)` passed where `Array::new()` was required ([issue #305](https://github.com/noib3/nvim-oxi/issues/305)).

## A working build needs four settings to agree

The first decision is which nvim-oxi to depend on, because **crates.io and `main` have diverged**. The crates.io 0.6.0 release offers `neovim-0-10`, `neovim-0-11` and `neovim-nightly`. Unreleased `main` dropped 0.10, added `neovim-0-12` (both on 2026-04-06), moved to edition 2024, and requires Rust 1.91 ([v0.6.0 Cargo.toml](https://github.com/noib3/nvim-oxi/blob/v0.6.0/Cargo.toml), [main Cargo.toml](https://github.com/noib3/nvim-oxi/blob/main/Cargo.toml)). Both versions' `build.rs` fail with `compile_error!` unless a version feature is enabled ([main build.rs](https://github.com/noib3/nvim-oxi/blob/main/build.rs)). The features are cumulative, and the maintainer says the effective target is `max(neovim-*)` ([issue #234](https://github.com/noib3/nvim-oxi/issues/234)). The CHANGELOG is unreliable here. It lists several post-release changes under "0.6.0", including an infallible `get_mode()`, `Buffer::get_name()` returning `String`, and the `OptionOpts` builder renaming `buffer` to `buf`. The `v0.6.0` tag does not contain them ([v0.6.0 source](https://github.com/noib3/nvim-oxi/tree/v0.6.0), [CHANGELOG](https://github.com/noib3/nvim-oxi/blob/main/CHANGELOG.md)). The official examples README still pins `nvim-oxi = "0.3"` and omits the feature flag ([examples/README.md](https://github.com/noib3/nvim-oxi/blob/main/examples/README.md)). Do not copy that snippet as-is.

The table below sets out what to use. The version mapping is inferred from the feature definitions and build scripts, not stated in nvim-oxi's docs.

| Target Neovim | Dependency line | Notes |
|---|---|---|
| 0.11.x | `nvim-oxi = { version = "0.6", features = ["neovim-0-11"] }` | Released crate. Matches real 2026 projects such as taohua.nvim ([Cargo.toml](https://github.com/dox4/taohua.nvim/blob/main/Cargo.toml)) |
| 0.12.x | `nvim-oxi = { git = "https://github.com/noib3/nvim-oxi", rev = "…", features = ["neovim-0-12"] }` | Only option. nomad depends on git master this way ([nomad Cargo.toml](https://raw.githubusercontent.com/nomad/nomad/main/Cargo.toml)). Requires Rust ≥ 1.91 |
| Nightly (0.13-dev) | git `main` with `neovim-nightly` | Layouts track a moving target |

The rest of the setup is mechanical but strict. Set `[lib] crate-type = ["cdylib"]`. Add a `.cargo/config.toml` that passes `-C link-arg=-undefined -C link-arg=dynamic_lookup` on both macOS targets, because Neovim's symbols "will only be available at runtime", and `/FORCE:MULTIPLE` on Windows MSVC targets, as nvim-oxi's own config does ([.cargo/config.toml](https://github.com/noib3/nvim-oxi/blob/main/.cargo/config.toml)). Then make the artifact findable. Cargo emits `libfoo.so`, `libfoo.dylib` or `foo.dll`. The official approach copies it to `lua/foo.so` (**also `.so` on macOS**) or `lua/foo.dll`, adds the parent directory to `runtimepath`, and calls `require("foo")` ([examples/README.md](https://github.com/noib3/nvim-oxi/blob/main/examples/README.md)). Many real plugins skip the copy and append `target/release/?.<ext>` and `lib?.<ext>` to `package.cpath`, choosing the extension from `jit.os`. taohua.nvim does this ([plugin/taohua.lua](https://github.com/dox4/taohua.nvim/blob/main/plugin/taohua.lua)), and strottos' template also falls back to `target/debug` and wraps the `require` in a `pcall` with a helpful error ([template init.lua](https://github.com/strottos/nvim_oxi_template/blob/main/lua/nvim_oxi_template/init.lua)). Because lazy.nvim's `opts = {}` cannot call into a Rust module directly, the usual answer is a thin Lua `setup(opts)` that `require`s the library and passes `opts` through ([issue #183](https://github.com/noib3/nvim-oxi/issues/183)).

Windows and Android are where builds go wrong. Enabling `mlua` on Windows has produced `LNK1181: cannot open input file 'lua5.1.lib'` ([issue #258](https://github.com/noib3/nvim-oxi/issues/258)). The maintainer says the `libuv` feature is untested on Windows because "I don't have access to a Windows machine" ([issue #234](https://github.com/noib3/nvim-oxi/issues/234)), and nvim-oxi's own test crate compiles libuv tests out on Windows ([tests/src/lib.rs](https://github.com/noib3/nvim-oxi/blob/main/tests/src/lib.rs)). On Termux, libuv builds fail with `cannot locate symbol "luv_loop"` ([issue #249](https://github.com/noib3/nvim-oxi/issues/249)). A plugin that must run everywhere should treat `libuv` as Unix-desktop-only.

## Tests run in real headless Neovim; async goes through one libuv handle

Testing is one of nvim-oxi's stronger features. With the `test` feature, `#[nvim_oxi::test]` replaces `#[test]`. Integration tests live in a separate `cdylib` crate whose `build.rs` is just `nvim_oxi::tests::build()`, and test names must be unique across the whole crate ([README](https://github.com/noib3/nvim-oxi)). The macro generates a hidden plugin entrypoint for each test, plus a host-side `#[test]` that spawns `nvim -u NONE --headless -i NONE -c "set noswapfile" -c "lua local f = package.loadlib(..., 'luaopen___<name>'); f()"`. Inside Neovim the body runs under `catch_unwind` and writes a fenced pass/fail result to stderr, which the host parses. A crash is reported as "Neovim segfaulted" instead of hanging ([test_macro.rs](https://github.com/noib3/nvim-oxi/blob/main/src/tests/test_macro.rs)). Tests may return `Result`, use `#[should_panic]`, and take a `cmd = "..."` attribute for setup commands ([test.rs](https://github.com/noib3/nvim-oxi/blob/main/crates/macros/src/test.rs)). Async tests use `test-terminator`. The test takes a `TestTerminator` and runs until `terminate()` is called, and if the terminator is dropped first, "the test will run forever" ([terminator.rs](https://github.com/noib3/nvim-oxi/blob/main/src/tests/terminator.rs)). For CI, nvim-oxi's own workflow is a good template. It runs ubuntu, macOS and Windows against Neovim v0.11.7, v0.12.0 and Nightly, installs Neovim with `rhysd/action-setup-vim`, maps each Neovim version to its feature flag, and runs a daily cron to catch nightly breakage ([ci.yaml](https://github.com/noib3/nvim-oxi/blob/main/.github/workflows/ci.yaml)). Mapping each Neovim version to its own feature flag is not optional. taohua.nvim's CI installs Neovim 0.10 while its crate enables `neovim-0-11`, which is exactly the kind of mismatch that causes layout bugs ([makefile.yml](https://github.com/dox4/taohua.nvim/blob/main/.github/workflows/makefile.yml)). Pure logic belongs in an ordinary module tested with plain `cargo test`, since every `#[nvim_oxi::test]` starts a fresh Neovim process.

Concurrency has one rule. The maintainer states that "all free-standing functions exposed by this library should only be called from the main thread" ([issue #260](https://github.com/noib3/nvim-oxi/issues/260)). The only sanctioned bridge is `libuv::AsyncHandle`. It is `Send + Sync`, and its callback "will always be executed on the main thread" ([async.rs](https://github.com/noib3/nvim-oxi/blob/main/crates/libuv/src/async.rs)). `TimerHandle::start`/`once` provide timers ([timer.rs](https://github.com/noib3/nvim-oxi/blob/main/crates/libuv/src/timer.rs)). The official pattern runs a `#[tokio::main]` function on a `std::thread`, sends data through an mpsc channel, calls `handle.send()`, and receives in the callback, wrapping editor calls in `schedule` to avoid textlock ([examples/libuv.rs](https://github.com/noib3/nvim-oxi/blob/main/examples/libuv.rs)). Two refinements are worth adopting, both inferred rather than documented. libuv coalesces multiple `send()` calls into one callback, so drain the channel with a `try_recv` loop instead of the example's single `blocking_recv`. And create every handle in the entrypoint, because creating an `AsyncHandle` off the main thread crashes Neovim. One user built a `!Send` `MainThreadToken` typestate to enforce this at compile time ([issue #260](https://github.com/noib3/nvim-oxi/issues/260)). nvim-oxi has no async/await executor. If you need mlua's `send` feature for async Lua, it conflicts with the `mlua/module` feature that nvim-oxi's `mlua` feature forces on. The workaround is to drop nvim-oxi's `mlua` feature and depend on mlua directly ([issue #286](https://github.com/noib3/nvim-oxi/issues/286)).

### Errors can crash the editor

nvim-oxi's main failure mode is a crash or abort rather than a Lua error. Returning `Err` from a `Function` callback or from the entrypoint, which the API appears to support, has crashed Neovim. A contributor suspects `lua_error`'s longjmp across Rust frames is unsound ([issue #231](https://github.com/noib3/nvim-oxi/issues/231)), and the fix PR #279 ("when error, return nil, not lua_error") is still open ([PRs](https://github.com/noib3/nvim-oxi/pulls?q=is%3Apr)). Layout drift produces "panic in a function that cannot unwind". Any `api::set_hl()` call aborts Neovim 0.12.2 because `SetHighlightOpts` still mirrors the 0.11.3 keyset, while 0.12 added five fields and reordered others ([issue #311](https://github.com/noib3/nvim-oxi/issues/311)). The runtime crates contain no `catch_unwind`. In practice, wrap each exported closure body in `std::panic::catch_unwind`, keep `panic = "unwind"`, and return an `{ ok, value | error }`-style result instead of `Err`, as taohua.nvim does ([taohua.nvim](https://github.com/dox4/taohua.nvim)). Logging from background threads goes through `tracing`, since `print!` is main-thread only ([issue #260](https://github.com/noib3/nvim-oxi/issues/260)). There is no hot reload. Once LuaJIT has loaded a library it stays mapped, so the development loop is to rebuild and restart Neovim. strottos' template automates this with a script that sets `NVIM_LOG_FILE` locally and launches a lazy.nvim test config ([run.sh](https://github.com/strottos/nvim_oxi_template/blob/main/scripts/run.sh)).

## Distribution means one binary per Neovim minor per platform

No nvim-oxi-specific installer exists. The baseline is lazy.nvim's `build` hook, which accepts a shell command, a Lua function or a build file ([lazy.nvim docs](https://lazy.folke.io/developers)). In practice that is `build = "cargo build --release"` or `build = "make"` ([taohua.nvim](https://github.com/dox4/taohua.nvim)). This works only for users with a Rust toolchain, and on `main` that means Rust 1.91 or newer.

The flagship nvim-oxi plugin shows what reaching other users costs. **nomad** (692 stars, real-time collaborative editing on custom CRDTs, by noib3) supports only lazy.nvim. It offers three builders: `download_prebuilt()`, `cargo()` (which "needs `cargo` from a nightly version of the Rust toolchain"), and `nix()` ([installation.md](https://raw.githubusercontent.com/nomad/nomad/main/docs/installation.md)). Its release assets are split **per Neovim version and per platform**, for example `nomad-2025.11.2-for-neovim-0.11-linux-x86_64.tar.gz`, and cover Linux and macOS only, with no Windows builds ([nomad releases](https://api.github.com/repos/nomad/nomad/releases)). This follows from the ABI coupling described above. A binary compiled with `neovim-0-11` struct layouts is not safe on 0.12.

The best-engineered distribution pipeline among Rust plugins belongs to blink.cmp, which uses mlua. Because mlua binds only LuaJIT's frozen C API, blink.cmp builds **one artifact per target triple**. It covers glibc and musl Linux, Android, macOS, Windows x86_64 and aarch64, and FreeBSD/OpenBSD, using `cross` or `cargo build`, then generates `.sha256` checksums and uploads to GitHub Releases ([release.yaml](https://github.com/Saghen/blink.cmp/blob/main/.github/workflows/release.yaml)). Prebuilt binaries are downloaded automatically when the user is on a release tag, and a pure-Lua fallback runs when the download fails ([blink.cmp fuzzy docs](https://cmp.saghen.dev/configuration/fuzzy)). An nvim-oxi plugin can copy this pipeline but has to multiply the matrix by the number of supported Neovim minors. The LuaRocks `rust-mlua` build backend, which simply runs cargo and copies the cdylib, should in principle work for nvim-oxi crates too, but no nvim-oxi plugin is known to use it ([luarocks-build-rust-mlua](https://github.com/mlua-rs/luarocks-build-rust-mlua)). Native modules have friction even with mlua. blink.cmp users still hit `luaopen_blink_cmp_fuzzy` "symbol not found" load errors ([discussion #2299](https://github.com/saghen/blink.cmp/discussions/2299)).

Real-world adoption beyond nomad is small. GitHub counts about 165 dependent repositories, but after the blink projects the top entries are nvim_winpick (55 stars), age.nvim (21) and a long tail of personal configs ([dependents](https://github.com/noib3/nvim-oxi/network/dependents)). crates.io lists five reverse dependencies ([crates.io](https://crates.io/api/v1/crates/nvim-oxi/reverse_dependencies)). The 2,410-star nvim-spectre ships an optional `spectre_oxi` engine still pinned to nvim-oxi 0.3 with `neovim-0-9` ([spectre_oxi Cargo.toml](https://raw.githubusercontent.com/nvim-pack/nvim-spectre/master/spectre_oxi/Cargo.toml)). Saghen built blink.nvim on nvim-oxi 0.5.1 ([blink.nvim Cargo.toml](https://raw.githubusercontent.com/saghen/blink.nvim/main/Cargo.toml)) but used mlua for the far more popular blink.cmp and blink.pairs ([blink.cmp Cargo.toml](https://raw.githubusercontent.com/Saghen/blink.cmp/main/Cargo.toml)). That suggests a preference for mlua in distributable plugins, though Saghen has not stated a reason publicly.

## A single maintainer and 17 months without a release

nvim-oxi is a polished design with a weak maintenance base. **noib3 has 752 commits; the next contributor has 25** ([contributors](https://api.github.com/repos/noib3/nvim-oxi/contributors)). The repository has 1,139 stars, 64 forks and 43 open issues and PRs, and its last push was 2026-05-17 ([GitHub API](https://api.github.com/repos/noib3/nvim-oxi)). Releases came roughly once or twice a year from 2022 to 2025, then stopped after 0.6.0. The crate totals 58,465 downloads, 5,323 of them in the last 90 days ([crates.io](https://crates.io/api/v1/crates/nvim-oxi)). Neovim has meanwhile shipped 0.12.0 through 0.12.6 (the last on 9 October 2026), and nightly is 0.13-dev ([Neovim releases](https://github.com/neovim/neovim/releases)). Master gained `neovim-0-12` eight days after 0.12.0 shipped, but the patch-release breakage that followed is unresolved. The open items include #309 (`create_autocmd` broken on 0.12.2), #298 (split windows fail on 0.12.0), #311 (`set_hl` abort, fix PR #312 opened the same day with no maintainer response), and PR #307 (the autocmd `buffer`→`buf` rename) ([issues](https://github.com/noib3/nvim-oxi/issues), [issue #311](https://github.com/noib3/nvim-oxi/issues/311)). There are also long-standing soundness and memory issues: a leak in `luajit::function::remove` (#283), an arena that is never freed (#284), and handles that "should not be sent" across threads (#282) ([issues](https://github.com/noib3/nvim-oxi/issues)). Breaking API churn has also been steady. 0.5 renamed `module` to `plugin` and added an `EchoOpts` argument to `echo`. 0.6 reshaped `notify`, `feedkeys` and the highlight APIs. `main` deprecated `notify` and appears to have removed it ([CHANGELOG](https://github.com/noib3/nvim-oxi/blob/main/CHANGELOG.md)).

The most likely explanation is that noib3's attention is on nomad. nomad consumes nvim-oxi from git master, so the release gap hurts third-party users more than its author. No roadmap or 0.7 announcement exists, and nothing in the sources confirms activity after May 2026. Treat the open-PR status above as something to re-check before you commit. One sign of community dissatisfaction is **nvimo**, a fork by contributor c-c-k with 880 commits and no releases. It replaces nvim-oxi's hand-rolled Lua layer with mlua, citing mlua's "robust error and panic propagation across the Rust-Lua boundary" ([nvimo](https://github.com/c-c-k/nvimo)). Public discussion is otherwise sparse. The researchers found no recent r/neovim or Discourse threads, and the main forum signal is enthusiastic 2022 Hacker News comments imagining "a really slick and responsive editing experience" ([HN](https://news.ycombinator.com/item?id=32409080)).

## mlua wins most Rust-in-Neovim projects; nvim-oxi wins a narrow band

The real alternatives differ mainly in **what the binary is coupled to**. mlua in `module` mode also builds a LuaJIT-loadable `cdylib` and needs the same macOS `dynamic_lookup` flags. It is tested in module mode on Windows, macOS and Linux, but it reaches Neovim only through Lua's `vim.*` tables, so Neovim's internal structs never enter the ABI ([mlua README](https://github.com/mlua-rs/mlua)). It has about **130x nvim-oxi's downloads** (7.70M total, version 0.12.2, last push 2026-10-03) ([crates.io mlua](https://crates.io/api/v1/crates/mlua)) and powers avante.nvim (18k stars), fff (11k) and blink.cmp (6.6k) ([avante Cargo.toml](https://raw.githubusercontent.com/yetone/avante.nvim/main/Cargo.toml), [fff Cargo.toml](https://raw.githubusercontent.com/dmtrKovalenko/fff.nvim/main/Cargo.toml)). RPC via nvim-rs avoids ABI coupling by running a separate async process. Its API is labelled "unstable", it has 270 stars and its last release was March 2025 ([nvim-rs](https://github.com/KillTheMule/nvim-rs)). The older neovim-lib has had no push since 2019 ([neovim-lib](https://api.github.com/repos/daa84/neovim-lib)). WASM bridges such as wasm_nvim remain experiments ([wasm_nvim](https://github.com/Borwe/wasm_nvim)).

| Approach | Binary coupled to | Neovim API access | In-process callbacks | Distribution reality | Adoption (Oct 2026) |
|---|---|---|---|---|---|
| **nvim-oxi** | Neovim minor version (keyset layouts; patch releases have broken it) | Typed Rust wrappers of `nvim_*`; gaps in lsp, ui, diagnostic, treesitter, `vim.fn` | Yes | Per-Neovim-minor × per-platform; Windows shaky | 1.1k stars, 58k downloads |
| **mlua module** | LuaJIT 5.1 C ABI (frozen) | Anything Lua can reach, untyped | Yes | One binary per platform plus Lua fallback; all major OSes shipped | 2.9k stars, 7.7M downloads |
| **nvim-rs (RPC)** | Versioned msgpack-RPC API | Full RPC API, async | No keymap/schedule callbacks; IPC latency | Separate executable, no ABI risk | 270 stars, 209k downloads |
| **Pure Lua** | Nothing | Full, native | Yes | No build step | Dominant |

This leads to a clear rule of thumb. Write the plugin in Lua by default. If a hot path is CPU-bound (fuzzy matching over 10k+ items, indexing, parsing) or needs a Rust crate, add an mlua module with prebuilt binaries and a Lua fallback, the pattern blink.cmp uses for its claimed "~6x" speedup over fzf ([blink.cmp fuzzy docs](https://cmp.saghen.dev/configuration/fuzzy)). Reach for nvim-oxi only when the Rust side itself must make many editor calls (buffers, extmarks, autocmds, windows) and compile-time types for those calls are worth per-version builds. nomad's CRDT-plus-networking stack fits that description. Choose RPC when crash isolation or running outside Neovim matters more than callback latency. Nobody has published independent benchmarks of call overhead across these approaches, so performance arguments for nvim-oxi over mlua are untested.

## Conclusion

nvim-oxi's defining feature is also its main liability. Mirroring Neovim's option dictionaries as typed `#[repr(C)]` structs is what makes the API pleasant, and it is also what turns a Neovim patch release into a potential abort. Every downstream cost follows from that one choice: the per-version feature flags, nomad's per-version release assets, the 0.12.x crash backlog, and the shaky Windows support. mlua avoids all of it by binding the frozen LuaJIT ABI and leaving Neovim's API to Lua. The fact that the ecosystem's biggest Rust plugins, and even an nvim-oxi contributor's fork, chose mlua reads as a judgment on that trade-off, not as a matter of taste.

If you adopt nvim-oxi in October 2026, plan to own your dependency. Pin a `main` revision, be ready to carry patches such as PR #312, test against every supported Neovim minor with the matching feature flag, and never return `Err` across the Lua boundary. A useful hedge is a hybrid design. Keep most editor interaction in Lua or mlua, and confine nvim-oxi to code that genuinely benefits from typed direct API access, so that a stalled upstream or a Neovim keyset change damages a small, replaceable layer instead of the whole plugin.
