## Notes
- Public contract to document exactly (from `init.lua` line 46 and `commands.lua` lines 255-352,
  382-385): command name `:NovelistVale`; config `vale = { executable = 'vale' }`; supported
  filetypes `markdown` and `text` only; unsupported → WARN; named buffer passes `--path=<name>`,
  unnamed passes `--ext=.md`/`.txt`; adapter stdin = current buffer lines joined with `\n`; findings
  use `vim.fn.setloclist(winid, ...)` with title `Novelist Vale` and `lopen` only when items exist;
  zero findings → INFO `novelist: no Vale findings`; process/parse error → ERROR `Vale check
  failed: ...` with prior location list untouched; window no longer displaying the source buffer →
  WARN `Vale results could not be displayed in the invoking window`. No `setqflist`/`copen` is used.
- `make docs-check` runs `helptags doc` and resolves `:help novelist`; it leaves `doc/tags` behind,
  so `make clean` is required afterward unless the release process wants tags tracked (README and
  vimdoc both already state this).
- Doc-consistency skill (`~/.agents/skills/doc-consistency`): match existing heading/list/table
  styles, keep README `lua` fences and vimdoc `>lua`/`>` blocks, keep example values illustrative
  and consistent, and update docs in the same change as the implementation they describe. README
  and vimdoc must agree on config key/default, command, filetypes, async/unsaved behavior,
  location-list vs quickfix, and the optional-dependency boundary.
- Scope guard: only `README.md` and `doc/novelist.txt` are edited (plus the two planning files);
  no implementation/test changes, no Vale config/styles, no manager-specific install snippets, and

## Discovered
- Manual Vale smoke (real `/usr/bin/vale` 3.20.0, Neovim 0.12.5 headless) exposed an adapter defect
  outside this task's file scope. `lua/novelist/vale.lua` appends a `'-'` positional to argv; Vale
  3.20.0 returns `{}` (exit 0) when `-` is passed as the file argument, even though the same stdin
  with `--path=<file>` and no `-` produces findings (exit 1). Observed: CLI
  `printf '...' | vale --output=JSON --path=draft.md -` -> `{}` exit 0; `cat draft.md | vale
  --output=JSON --path=draft.md` -> finding on the repeated word, exit 1; headless `:NovelistVale`
  on the unsaved named buffer -> loclist count 0 and "novelist: no Vale findings". The documented
  intended contract is unchanged, but real-Vale findings are not currently reproducible, so the
  manual smoke must not be recorded as a pass. Fixing `vale.lua` is out of scope for 3.3.1 and
  needs a separate decision.
